# Submit Patent Search

Submit a new patent search to IntelliPat. It runs asynchronously; a real search usually takes **about 1.5–2.5 hours**.

**Serve-then-charge.** Submitting a search charges nothing. The response's `credits_charged_micros` is `0` and `quoted_micros` carries the quote: what the search is expected to cost at the requested tier. You need at least the quote in available credits to submit. The charge lands **after the search completes**: its measured cost, **never more than twice the quote**. A search that fails is not charged. Every submission carries an `idempotency_key` generated by this skill, so retrying the same submission returns the original job instead of starting a second one.

All calls go through the `intellipat` MCP server that this plugin registers. It provides the tools `get_credits`, `submit_search`, `get_job_status`, `get_report_summary` and `get_report`. Call them as tools; there is no URL or key to handle in the conversation.

## Step 1: Check the connection and show the balance

Call **`get_credits`**.

- If the tool is unavailable, or the call fails with an authentication error (missing, invalid or revoked API key), print this and **stop**:

  ```
  The IntelliPat plugin is not connected. Set your API key in the environment Claude Code starts from:

    export INTELLIPAT_MCP_API_KEY="ip_..."

  Create a key at https://console.intellipat.ai (API keys page), then restart Claude Code.
  ```

- On success, the tool result has `balance_micros` (an integer; 1,000,000 micros = 1 credit) and `balance_usd`. Show the balance in credits.

**Reading any tool result.** Check whether the result is an error first. When it is, the reason is in the result's structured content as `{"error": "<code>", ...}`, or for not-found and not-yours as plain text. Otherwise the data is in the structured content (the same JSON also appears as text).

## Step 2: Collect the search inputs

Ask for these fields. Ask several at once where it is natural.

| Field | Type | Notes |
|---|---|---|
| `title_matter` | string | A short, human-readable title. Used in memory and reports. |
| `search_type` | enum | `novelty` (default) or `invalidity`. |
| `claim_text` | string | The claim or invention text (an independent claim is best). |
| `primary_features` | string[] | **Required for a novelty search.** A non-empty list of non-empty strings, each one feature of the claim. The service does **not** derive features from `claim_text`; a novelty search without them is refused (`invalid_features`). See below. |
| `before_date` | string | Optional priority cut-off, `YYYY-MM-DD` (a real calendar date). Prior art must predate it. |

Optional:

| Field | Notes |
|---|---|
| `secondary_features` | Additional context features (default: none). |
| `claims` | Invalidity only: an array of `{claim_text, primary_features, secondary_features}`, one per claim. |
| `tier` | Search depth: `screen`, `standard` (default) or `deep`. A tier scales how much work the search does, and so what it costs. Ask only if the user mentions depth, speed or budget; otherwise send `standard`. |
| `idempotency_key` | **Generated by this skill, never asked of the user** (Step 3). |

### Proposing primary features

Give the claim's main features, usually 4–7 (3–8 works well). At least one is required; there is no fixed maximum. More features make a search take longer; the quoted price is set by the tier, not the feature count.

Parse `claim_text` and propose features: the claim's elements and functional limitations. For example, for

> "A method comprising: receiving a request from a client; validating the request against a stored token; and returning a response."

propose:
- receiving a request from a client
- validating the request against a stored token
- returning a response

Show the list and ask: "Use these features, or edit the list?" **Do not submit a novelty search until the user has confirmed a non-empty feature list.**

## Step 3: Submit

### 3a: Generate the idempotency key

Generate one fresh key per **logical submission** (per distinct search the user asked for) before the first call, and reuse the *same* value for every retry of that submission:

```bash
IDEMPOTENCY_KEY=$(cat /proc/sys/kernel/random/uuid 2>/dev/null || uuidgen || python3 -c 'import uuid; print(uuid.uuid4())')
```

A new search (different claim text, features, date or tier) **must** get a new key. A repeat with an old key returns the old job, whatever arguments accompany it, so changing the tier of a submitted search means a new submission with a new key.

### 3b: Call `submit_search`

Call **`submit_search`** with `title_matter`, `search_type`, `claim_text`, `primary_features` (and `secondary_features` / `claims` if collected), `tier` and `idempotency_key`. Include `before_date` if the user gave one.

### 3c: Read the result

**Success** (not an error): `{"job_id": "<id>", "status": "pending", "credits_charged_micros": 0, "quoted_micros": <int>}`. A replayed retry may also carry a `message`.
- **Nothing has been charged yet.** Tell the user the search was submitted and show the quote: `quoted_micros / 1,000,000` credits, *charged when the search completes, at most twice the quote; a failed search is not charged*. If `quoted_micros` is absent, an older server answered: say the price is shown on the credits page once the search completes.
- `job_id` has one of two shapes; accept and show both. It is a **32-character hex** string when derived from your `idempotency_key`, or a **20-character** id otherwise. Never reject a job id for its length.
- Compare `status` case-insensitively and store it lowercase.

**Error result**: `error` is one of:

| `error` | Meaning | What to do |
|---|---|---|
| `invalid_features` | A novelty search without a usable `primary_features` list. **Nothing was started or charged.** | Propose features (Step 2), confirm, resubmit with the **same** key. |
| `invalid_before_date` | `before_date` is not a real `YYYY-MM-DD` date. **Nothing was started or charged.** | Fix or drop the date, resubmit with the **same** key. |
| `invalid_tier` | `tier` is not `screen` / `standard` / `deep`. Nothing was started or charged. | Fix it, resubmit with the **same** key. |
| `invalid_idempotency_key` | The key was not a 1–128 character string. Nothing was started. | A skill bug: regenerate the key (3a) and resubmit. |
| `insufficient_credits` | Not enough available credits to cover the quote. **Nothing was started or charged.** | Show `balance` from the result, point the user to the credits page at https://console.intellipat.ai. |
| `quote_unavailable` | The service could not price the search right now. Nothing was started or charged. | Tell the user; suggest trying again shortly (same key). |
| `enqueue_failed` | The search could not be queued. **Nothing was charged**; the job is recorded as failed. | Tell the user nothing is running and nothing is owed. Resubmit only on their confirmation, with a **new** key (the old key returns this same result). |

Only a non-error result with a `job_id` is a submitted search.

## Step 4: Record the job in project memory

```bash
PROJECT_KEY=$(echo "$PWD" | sed 's|/|-|g' | sed 's|^-||')
MEMORY_DIR="$HOME/.claude/projects/$PROJECT_KEY/memory"
mkdir -p "$MEMORY_DIR"
MEMORY_FILE="$MEMORY_DIR/intellipat_jobs.md"
```

If `intellipat_jobs.md` does not exist, create it with the header `# Intellipat Jobs`. Append, keeping the `- key: value` lines exactly (the session-start hook greps `status:`):

```markdown
## <job_id>
- title_matter: <title_matter>
- search_type: <novelty|invalidity>
- status: pending
- submitted_at: <ISO 8601 UTC, e.g. 2026-11-17T14:30:00Z>
- quoted_credits: <quoted_micros / 1_000_000, or "unknown">
- tier: <screen|standard|deep>
- idempotency_key: <the key sent>
- before_date: <YYYY-MM-DD, or omitted>
- project_context: <one line on why this search was run, from the conversation>
- last_checked_at: <same as submitted_at>
```

Add one line to `MEMORY.md` if it is not already there:

```
- [intellipat_jobs.md](intellipat_jobs.md): IntelliPat patent-search jobs (status, results, project context)
```

## Step 5: Offer polling

> Check job `<job_id>` every hour? (y/n)

If yes, schedule `/check-job-status <job_id>` hourly (a scheduling tool such as CronCreate, if available). Otherwise tell the user they can run `/check-job-status <job_id>` or `/review-pending-jobs` at any time.

## Error handling

- **Authentication errors** (missing, invalid or revoked key): show the setup message from Step 1. Do not retry.
- **Error results**: the table in 3c. Every row is a definite outcome; none needs a guess.
- **No response, a timeout, or a result you cannot read, on `submit_search`:** retry the *identical* call with the **same `idempotency_key`**, up to 3 times (pause 10 s, 30 s, 60 s). The service returns the original job for that key and starts nothing new, so retrying is safe: you end with one job. A retry that returns `status: pending` with a `message` is the same job, still being created; proceed as a success. If `/check-job-status` then reports the job **not found** on every check for more than 10 minutes, the earlier attempt did not complete: tell the user, and resubmit **with a NEW key** only on their confirmation. Never reuse a key for a different search.

Never claim a job was submitted unless the result is not an error and contains a `job_id`.
