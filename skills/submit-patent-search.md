# Submit Patent Search

Submit a new patent search job to the Intellipat MCP service. A search is charged to your credit balance (currently **$1.00 USD** = 1,000,000 credit micros, a price configured server-side) and runs asynchronously — typical turnaround is 15–45 minutes.

**Charge-then-serve contract.** The server charges your balance *before* it creates the job. A success result means a job exists and was charged for the amount it reports; an `isError` result means no search was started (or, for `enqueue_failed`, that the charge was refunded). Every submission carries a client-generated `idempotency_key`, so a retry of the same submission returns the original job instead of charging again — see Step 4 and Error handling.

## Step 1 — Verify environment

Both env vars must be set before any MCP call:

```bash
[ -n "$INTELLIPAT_MCP_URL" ] && [ -n "$INTELLIPAT_MCP_API_KEY" ] && echo OK || echo MISSING
```

If missing, print this and **stop** (do not prompt for anything else):

```
Intellipat MCP plugin is not configured. Set these env vars (e.g. in ~/.bashrc or your shell profile):

  export INTELLIPAT_MCP_URL="https://<your-lambda-url>.lambda-url.us-east-2.on.aws/"
  export INTELLIPAT_MCP_API_KEY="ip_..."

Create an API key at https://app.intellipat.ai/settings/api-keys
Then restart your Claude Code session and re-run /submit-patent-search.
```

## Step 2 — Show credit balance

Call `get_credits` and display balance in USD before collecting input. If the balance is below the expected cost (currently $1.00), warn the user and offer to stop.

**Reading any response.** Every call returns JSON-RPC. On success the tool's data is in `result.structuredContent` (the same JSON is in `result.content[0].text`). Check `result.isError` first: when `true`, the failure is described by `structuredContent` (e.g. `{"error": "insufficient_credits", ...}`) or, for not-found / not-yours, by the text in `content[0].text`. A top-level `error` (not `result`) is a protocol/auth failure — HTTP 401 means the key is missing, invalid or revoked (`error.data.code` is `no_credentials` or `invalid_api_key`).


```bash
curl -s -X POST "$INTELLIPAT_MCP_URL" \
  -H "Content-Type: application/json" \
  -H "X-Api-Key: $INTELLIPAT_MCP_API_KEY" \
  -d '{"jsonrpc":"2.0","id":"1","method":"tools/call","params":{"name":"get_credits","arguments":{}}}'
```

Read `result.structuredContent.balance_usd` (and `balance_micros`, an integer). Auto-reload settings are in `auto_reload_enabled`, `auto_reload_threshold_micros`, `auto_reload_amount_micros`. (The MCP *response* has no `creditBalanceMicros` key — that is the name of the underlying Firestore field, which the server maps to `balance_micros`.)

## Step 3 — Collect search inputs

Use AskUserQuestion (or plain prompts if multi-field) to collect all fields. Required fields:

| Field | Type | Notes |
|---|---|---|
| `title_matter` | string | Short human-readable title for the search. Used in memory and reports. |
| `search_type` | enum | One of `novelty`, `invalidity`, `sanitized`. |
| `claim_text` | string | The full claim text (independent claim recommended). For invalidity, this can be a single claim or the lead independent claim. |
| `before_date` | string | Priority date in `YYYY-MM-DD` format. Prior art must be before this date. |
| `primary_features` | string[] | List of key claim features to search on. **You should suggest these by extracting noun phrases / functional limitations from `claim_text`, then ask the user to confirm or edit.** Aim for 3–8 features. |

Optional fields:

| Field | Notes |
|---|---|
| `secondary_features` | Additional context features (default: empty). |
| `claims` | Invalidity only: array of `{claim_text, primary_features, secondary_features}`, one per claim. |
| `tier` | Search depth: `screen`, `standard` (default) or `deep`. Ask only if the user mentions depth, speed or budget; otherwise send `standard`. The amount charged is whatever the response's `credits_charged_micros` says. Needs a server that lists `tier` in `tools/list` (see Step 4); omit it otherwise. |
| `idempotency_key` | **Generated by this skill, never asked of the user** — Step 4. |

(The server does not currently read `preamble` or `general_text`; do not collect them.)

### Extracting primary features

When the user provides `claim_text`, parse it locally and propose a list of features. Example for a method claim:

> "A method comprising: receiving a request from a client; validating the request against a stored token; and returning a response."

Suggested features:
- receiving a request from a client
- validating the request against a stored token
- returning a response

Show the suggested list and ask: "Use these features, or edit the list?" Accept user edits before submitting.

## Step 4 — Submit the search

### 4a — Check what the server supports (once per session)

Call `tools/list` and read the `submit_search` entry's `inputSchema.properties`:

```bash
curl -s -X POST "$INTELLIPAT_MCP_URL" \
  -H "Content-Type: application/json" \
  -H "X-Api-Key: $INTELLIPAT_MCP_API_KEY" \
  -d '{"jsonrpc":"2.0","id":"1","method":"tools/list"}'
```

- `idempotency_key` present → **keyed server**: use the retry rules below.
- absent → **legacy server**: it ignores arguments it does not know. Send no `idempotency_key`, and treat the outcome of a lost response as undeterminable (legacy rule in Error handling).
- If `tools/list` cannot be read (no response, non-200, or unparsable JSON), treat the server as legacy for this session.
- `tier` present → `tier` may be sent; absent → omit it.

### 4b — Generate the idempotency key (keyed server only)

One fresh key per **logical submission** — i.e. per distinct search the user asked for. Generate it once, before the first call, and reuse the *same* value for every retry of that submission:

```bash
IDEMPOTENCY_KEY=$(cat /proc/sys/kernel/random/uuid 2>/dev/null || uuidgen || python3 -c 'import uuid; print(uuid.uuid4())')
```

A new search (different claim text, features, date, or tier) **must** get a new key. Changing the `tier` of a search already submitted is a new submission with a new key; a repeat with the old key returns the old job, whatever arguments accompany it.

### 4c — Call submit_search

```bash
curl -s -X POST "$INTELLIPAT_MCP_URL" \
  -H "Content-Type: application/json" \
  -H "X-Api-Key: $INTELLIPAT_MCP_API_KEY" \
  -d "$(cat <<JSON
{"jsonrpc":"2.0","id":"1","method":"tools/call","params":{"name":"submit_search","arguments":{
  "title_matter": "...",
  "search_type": "novelty",
  "claim_text": "...",
  "before_date": "2024-01-15",
  "primary_features": ["...", "..."],
  "tier": "standard",
  "idempotency_key": "$IDEMPOTENCY_KEY"
}}}
JSON
)"
```

### 4d — Read the result

On success `result.structuredContent` is `{"job_id": "<id>", "status": "pending", "credits_charged_micros": <int>}` (a replayed retry may also carry a `message`). Compare statuses case-insensitively and store them lowercase in memory (a defensive rule: server builds from before the status-enum fix returned `PENDING`).

**`job_id` has two shapes — accept and display both:** a **32-character hex** string when the server derived it from your `idempotency_key`, or a **20-character** id when no key was sent (legacy server, or no key). Never validate a job id against one fixed length. If you sent a key and received a 20-character id, the server ignored the key: treat it as a legacy server for the rest of this session (no keyed retries).

**On success the charge happened.** `credits_charged_micros` is the amount actually charged for this job and appears only on success; record it as the amount charged (`credits_cost_usd` = `credits_charged_micros / 1_000_000`). Tell the user the search was submitted and charged that amount.

**On `result.isError`**, `structuredContent.error` is one of:

| `error` | Meaning | What to do |
|---|---|---|
| `insufficient_credits` | Balance below the cost. **No job was started, nothing charged.** | Show `structuredContent.balance`, point to `https://app.intellipat.ai/settings/credits`. |
| `invalid_idempotency_key` | Key was not a 1–128 character string. Nothing sent, nothing charged. | A skill bug — regenerate the key (Step 4b) and resubmit. |
| `invalid_tier` | `tier` not one of `screen` / `standard` / `deep`. Nothing charged. | Fix the value and resubmit with the **same** key (nothing was created). |
| `charge_failed` | The charge could not be made. **No job was started.** `job_id` is present but refers to no job. | Tell the user; do not retry automatically. Suggest checking the credits page, then `/submit-patent-search` again (a **new** key). |
| `enqueue_failed` | Charged, but the job could not be queued; **the charge was refunded** and the job (`job_id`) is recorded as `error`. | Tell the user nothing is running and nothing is owed. Resubmit only on confirmation, with a **new** key — a repeat with the old key returns this same error, never a new job. |

Only an `isError: false` result with a `job_id` is a submitted search.

## Step 5 — Persist to project memory

Save the job to project memory at `intellipat_jobs.md`. Determine the project memory directory:

```bash
PROJECT_KEY=$(echo "$PWD" | sed 's|/|-|g' | sed 's|^-||')
MEMORY_DIR="$HOME/.claude/projects/$PROJECT_KEY/memory"
mkdir -p "$MEMORY_DIR"
MEMORY_FILE="$MEMORY_DIR/intellipat_jobs.md"
```

Append a job entry in this exact format (preserving the `- ` and `key: value` lines so the session-start hook can grep `status:`):

```markdown
## <job_id>
- title_matter: <title_matter>
- search_type: <novelty|invalidity|sanitized>
- status: pending
- submitted_at: <ISO 8601 UTC, e.g. 2026-05-08T14:30:00Z>
- credits_cost_usd: <credits_charged_micros / 1_000_000 — the amount charged for this job>
- tier: <screen|standard|deep, or omitted if not sent>
- idempotency_key: <the key sent, or omitted for a legacy server>
- before_date: <YYYY-MM-DD>
- project_context: <one-line description of why this search was run, drawn from current conversation>
- last_checked_at: <same as submitted_at>
```

If `intellipat_jobs.md` does not exist, create it with a top-level header `# Intellipat Jobs` first, then append. Also add a one-line pointer in `MEMORY.md` if not already present:

```
- [intellipat_jobs.md](intellipat_jobs.md) — Active and historical Intellipat patent-search jobs (status, results, project context)
```

## Step 6 — Offer polling

After the job is saved, offer to start a recurring status check:

> Poll job `<job_id>` every 30 minutes via CronCreate? (y/n)

If yes, use `CronCreate` to schedule `/check-job-status <job_id>` every 1800 seconds. If no, tell the user they can run `/check-job-status <job_id>` or `/review-pending-jobs` manually.

## Error handling

- Top-level JSON-RPC `error` / non-200 HTTP status: surface `error.message` verbatim. Do not save anything to memory.
- HTTP 401 (`error.data.code` = `no_credentials` / `invalid_api_key`): tell the user the API key is missing, invalid or revoked, point them to `https://app.intellipat.ai/settings/api-keys`.
- HTTP 404 `Method not found: tools/call`: the server is an older, pre-protocol deployment. Tell the user the Intellipat MCP server needs to be upgraded; do not retry.
- `isError` tool results: the table in Step 4d. Every row there is a definite outcome — none of them needs a guess.
- **Network failure, timeout, or any response you cannot read, on `submit_search` — keyed server:** retry the *identical* request with the **same `idempotency_key`**, up to 3 times with a short pause (10 s, 30 s, 60 s). The server returns the original job for that key and does not charge again, so a retry is safe by contract; whether the first call reached the server or not, you end with one job and one charge. A retry that returns `status: pending` with a `message` is the same job, still being created — proceed as a success. Then, if `/check-job-status` reports that job **not found** on every check for more than 10 minutes, the earlier attempt did not complete: tell the user, and resubmit **with a NEW key** only on their confirmation. Never reuse a key for a different search.
- **Same failure — legacy server (no `idempotency_key` in `tools/list`, or a 20-character id came back for a keyed call):** the outcome is not determinable from the client. Do not retry, do not guess, and do not use the credit balance to decide. Tell the user plainly that a job may or may not have been created and charged, that the credits page's ledger lists charges with the job id in the description, and **re-submit only if the user explicitly confirms** after being told it may create a second job and a second charge. Never as an automatic retry.

Never claim a job was submitted unless the response contains a `job_id` and `isError` is `false`.
